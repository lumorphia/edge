# ADR-0001: 入口の Caddy を Prismtone から分け、全サービスのサイトをここにまとめる

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-18 |
| Deciders | t1nyb0x    |

## Context

同じ VPS で lumorphia/prismtone・lumorphia/accounts が動き、lumorphia/scenote が続く。80/443 は Prismtone の compose の `proxy` (Caddy) が持ち、ほかのサービスは VPS の `CADDY_SITES_DIR` に置いた `*.caddy` で載っていた。これには次の問題がある (2026-10-18 の相棒の指摘)。

- `proxy` が Prismtone の web の healthy を待つ (`depends_on`)。Prismtone の web が上がらないと、入口ごと上がらない
- Prismtone のデプロイが全サービスの入口を作り直す。2026-10-11 に Prismtone の #442 のマージで doco-cd が古い `SITE_ADDRESS` のまま Caddy を作り直し、新しいドメインが空の 200 になった
- 共通の設定 (Cloudflare の IP、Origin CA の証明書、`*.caddy` を読む仕組み) の持ち主が Prismtone で、ほかのサービスの手順がそれを前提にしている
- `*.caddy` は VPS に手で写して reload する。どの設定が動いているかが Git から分からない

## Decision

- 入口を新しいリポジトリ `lumorphia/edge` (public、AGPL-3.0-only) に分ける。Caddy だけを動かし、どのサービスの起動も待たない
- 全サービスのサイトを edge の `Caddyfile` にまとめる (相棒の判断)。サービスを足すときは edge にも PR を出す
- `Caddyfile` はイメージ (`ghcr.io/lumorphia/edge-caddy`) に入れる。main への push で CI が作って `latest` を付け、edge 専用の doco-cd が入れ替える。VPS にファイルを手で写さない。doco-cd がリポジトリのファイルを bind mount するときにホストからどう見えるかは確かめておらず、それに頼らない
- 証明書 (Origin CA の 1 枚) は VPS の `EDGE_CERTS_DIR` から渡す
- 上流はサービスごとに固有の別名 (`<サービス>-web`) で、各サービスの web は `lumorphia-edge` にその別名で出る。Prismtone の web も `prismtone-web` で出る (今は Prismtone の中のネットワークだけ)
- ブランチは develop → main。main への反映がそのまま本番なので、段を 1 つ置く

## Consequences

### 良い点

- サービスのデプロイや障害が、ほかのサービスの入口に響かない。落ちたサービスのドメインが 502 になるだけ
- 入口の全体が 1 つのファイルで分かり、動いている設定がイメージの sha で分かる

### 悪い点・受け入れるリスク

- 入口の変更でも Caddy が作り直され、全ドメインが数秒止まる (reload ではない)
- サービスを足すときに、サービスのリポジトリと edge の 2 か所に PR が要る
- 切り替えのときに、入口が数秒止まる (docs/runbook/cutover.md)

## Alternatives

- Prismtone のままにする: 上の問題が残る
- lumorphia/platform に置く: platform は npm のパッケージと release-please のリポジトリで、本番の設定が混ざる
- サイトの設定は各サービスに残す (`*.caddy`): サービスと一緒に変えられるが、VPS に手で写す手順と、Git と本番のずれが残る
- Caddyfile を bind mount で渡す: 手で写すか、doco-cd のパスの扱いを確かめる必要がある
